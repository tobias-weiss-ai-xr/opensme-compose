DISCOVERY
  * Ollama/AI is NOT deployed on this host (no ai container) — delivered
    code + mocked tests only, no live-LLM gating, exactly as tasked.
  * The Rust backend has no single-note GET (only list POST/GET, :id
    DELETE, /files/:token/:name) — fetchIntercomThread fetches the whole
    list with the caller's cookie and filters by id (broadcast route's
    forwardToBackend pattern; the page.tsx API_BASE pattern carries no
    session, which the intercom requires).
  * Previous tasks were REJECTED for portal/web/docs/af-int-*.txt
    (outside portal/web/src/ + docs/ scope — see the T1 prompt's attempt
    log), so this report lives at the repo-root docs/ like T1–T5.
  * OLLAMA_URL/OLLAMA_MODEL naming already exists in the repo (analysis
    stack, README); the AI card uses AI_API_URL — T6 keeps the tasked
    OLLAMA_URL gate for the intercom AI row and reads AI_MODEL first,
    falling back to OLLAMA_MODEL then llama3.1.
  * Dedicated route folders (api/ai/summarize, api/ai/draft) beat the
    [[...path]] catch-all by Next.js segment precedence — no
    next.config/rewrite changes needed (same mechanism as /api/broadcast).
  * jsdom's DOMException is not `instanceof Error` — the timeout detection
    reads err.name structurally, and the probe effect additionally has a
    .catch guard so even misbehaving mocks can never produce an unhandled
    rejection ("no error spam").

DESIGN NOTES
  * Operator opt-in identical in spirit to INTERCOM_BROADCAST/AI_API_URL:
    OLLAMA_URL unset → route answers 503 {enabled:false}, the UI probe
    hides the row — the surface simply disappears, no error spam, and
    requests still 503 before reading the body.
  * Thin routes, fat lib: both routes are ~15 lines; the whole pipeline
    (gate → validate → session hop → transcript → prompt → LLM) lives in
    lib/llm.ts, which imports no next/* and is fully unit-testable with a
    stubbed fetch.
  * lib/ai.ts (browser) is deliberately separate from lib/api.ts: the
    legacy IntercomPanel suite mocks @/lib/api wholesale with an explicit
    factory, so a new import there would have forced edits to that file's
    mock and risked its assertions; the separate module also isolates the
    swallow-everything probe contract.
  * The draft prompt marks the target note inline ('← Antwort-Ziel') so
    one transcript serves both summarize (whole thread) and draft
    (anchored reply) without route-specific plumbing.
  * LlmError messages are user-facing German ('KI nicht erreichbar',
    'KI-Antwort fehlgeschlagen (HTTP …)'); technical causes ride the
    error's detail field for server logs only.

KNOWN LIMITATIONS
  * No live LLM verification possible on this host (no ai container) —
    the /api/chat contract is pinned against mocks; first live deployment
    should smoke-test with OLLAMA_URL + AI_MODEL set on portal-web.
  * The transcript cap (40 notes) bounds prompt size; the Rust store's
    own INTERCOM_MAX_MESSAGES cap applies upstream.
  * Compose wiring (OLLAMA_URL/AI_MODEL env on portal-web, ai service)
    is out of scope for this task.
  * AI_TIMEOUT_MS default 120 s assumes a local/small model; larger
    models may need the operator to raise it (the UI shows '…' while
    waiting, buttons disabled).
