DISCOVERY
  * /api/announcements (tests/05-e2e/broadcast.py, Epic H) is the
    PORTAL_ANNOUNCEMENTS env banner feature — unrelated to the intercom;
    T4 rides the intercom store instead (notes), as tasked.
  * IntercomPanel delta-polls ?since= every 7 s and prepends the POST
    response — the broadcast box reuses exactly that prepend pattern, so a
    broadcast appears instantly without an extra fetch.
  * The [[...path]] catch-all forwards only a fixed header set; the
    broadcast route forwards content-type + cookie itself and calls
    forwardToBackend directly (thin route, fanout lives in lib/broadcast.ts).
  * portal-web image = Next standalone (node:22-alpine, read-only rootfs,
    USER nextjs, network_mode service:portal, no python3, no scripts/
    mount): the SMTP send cannot live in the route — hence the child_process
    shell-out to scripts/broadcast-fanout.sh. In the image the script is
    absent by design: the operator mounts it and sets BROADCAST_FANOUT_SCRIPT
    (dev default walks upward from cwd and finds <repo>/scripts/…).
  * Stalwart publishes host ports 25/143/587/465/993; 25 is the plain,
    unauthenticated compose-internal listener (the route/script default),
    587 expects STARTTLS (unverified context in the script, no SMTP auth —
    the demo stack has a self-signed cert).
  * Stalwart principals auto-provision on a user's FIRST SSO login: on a
    fresh stack only testuser has a mailbox, the other 13 demo users 550
    '5.1.2 Mailbox does not exist.' — so the script sends per recipient
    (best-effort) and REPORTS the missing ones instead of failing the leg.
  * Measured stalwart listener: ~4.5 s per SMTP connection (slow greet);
    14 sequential connections = 65 s — too slow for the route's execFile
    budget. 5 parallel workers bring it to ~5 s; script/lib timeouts 20 s
    per connection / 60 s total.
  * A 14-RCPT single-message send makes stalwart drop the session
    ('Connection unexpectedly closed') — per-recipient transactions
    sidestep this entirely.

PROVISIONING
  * Recipients default to bootstrap/demo-users.json (13 company users +
    testuser, demo_email() = localpart@opensme.local), matching
    provision-demo-users.sh's USERS_JSON.
  * Only mailboxes whose principal exists receive mail; the operator sees
    'delivered 1/14 recipient(s)' + the missing list on stderr. After the
    demo users' first SSO logins the same broadcast reaches all 14.

DESIGN NOTES
  * Thin route, fat lib: all fanout logic is unit-testable in
    lib/broadcast.ts (fetch + execFile stubbed); the route only gates,
    validates, forwards and shapes the response.
  * Best-effort contract: the note is stored FIRST; Element/mail failures
    never fail the request — the UI status line names each channel with
    its detail ('Broadcast gesendet, aber: Element ✗ (…) · Mail ✓').
  * Element flow mirrors booking-notify.sh 1:1 (login body shape, v3
    endpoints, txn-id idempotency, alias directory resolve, no auto-create
    from the route) minus the --loop/state machinery that only the
    operator script needs.
  * The env-quote-hardened dotenv loader block is byte-identical across
    booking-notify.sh / broadcast-fanout.sh (check_env_quote.py pins it).
  * Secrets discipline: Matrix password/token never appear in details or
    logs (login failures report only 'HTTP <status>'); the mail leg is
    secretless (plain port 25 inside the compose network); set +x in both
    shell and python paths.

KNOWN LIMITATIONS
  * The deployed portal-web container needs operator wiring to enable the
    feature (compose is out of scope for this task):
      1. environment INTERCOM_BROADCAST=1 on portal-web
      2. mount scripts/broadcast-fanout.sh into the container (read-only,
         e.g. /opt/opensme/broadcast-fanout.sh) and set
         BROADCAST_FANOUT_SCRIPT=/opt/opensme/broadcast-fanout.sh
         (bash + jq + python3 are also required inside the image — none
         are present today; mounting a small sidecar image or executing
         via docker exec from a wrapper are the two clean options)
      3. optional: MATRIX_DOMAIN/MATRIX_ROOM/BROADCAST_MAIL_TO/
         BROADCAST_SMTP_* overrides — defaults already match the demo stack
  * 13 of 14 demo mailboxes stay 'missing' until first SSO login
    (auto-provisioning) — reported, not fatal.
  * The mail leg assumes unauthenticated port 25; port 587 works with
    STARTTLS but without SMTP auth (stalwart submission policy may refuse
    relay — 25 is the supported path).
  * Without INTERCOM_BROADCAST the route 404s (same observable as the
    catch-all's '404 hides backend surface' stance).
