T1-sogo-drafts — SOGo AI draft reply + inbox brief (IMAP APPEND handoff)
========================================================================
Campaign: ai-deeper (agentflow, worktree tf/T1-sogo-drafts @ a36c558).
Zero SOGo modification — the draft reaches the webmail user through the
mail store itself: the bot composes a German reply, APPENDs it to the
Drafts mailbox with the \Draft flag, and it shows up in SOGo under
„Entwürfe" for review & sending.

DELIVERABLES
------------
1. scripts/ai-room-bot.py (extended in place, still stdlib-only — the
   bind-mounted opensme-ai-bot container picks it up on restart; no new
   file, no rebuild):
     * '!entwurf <empfänger>: <stichpunkte>'  → LLM composes a German
       business e-mail (dedicated DRAFT_SYSTEM_PROMPT, contract: first
       line 'Betreff: …', then blank line, then Anrede/2-4 Absätze/
       Grußformel; tolerant split_draft_answer falls back to
       subject „Entwurf" when the model skips the line) → RFC-5322
       message built with email.message.EmailMessage (From = bot mail
       identity, To, Subject, Date, Message-ID, text/plain utf-8 body,
       CRLF line endings per RFC 3501) → imaplib APPEND '"Drafts"' with
       flags (\Draft) → room reply:
       „✉️ Entwurf liegt in SOGo unter „Entwürfe“ — An: … · Betreff: ….
        Bitte dort prüfen und senden."
       Missing mailbox handled: first APPEND answered NO [TRYCREATE] →
       automatic CREATE → single retry (works on virgin accounts).
     * '!brief' → inbox brief posted back: total + unread counts
       (EXAMINE INBOX readonly + SEARCH UNSEEN) plus the newest
       AI_BRIEF_LIMIT (default 8) items as
       „<n>. <dd.mm. hh:mm> — <Absender>: <Betreff>" — headers fetched
       with BODY.PEEK so nothing is ever marked read; list is newest
       first, truncated with a „(+N ältere nicht angezeigt)" tail.
     * Dispatch: handle_event now routes '!entwurf'/'!brief' bodies to
       handle_command BEFORE the '!ai' trigger; existing guards
       unchanged (own sender == login user_id ignored, '📅' booking
       announcements ignored, m.text only, PUT send with fresh UUID
       txn). Bare '!entwurf' / missing ':' → German usage text with a
       full example; unknown '!briefx' → „Unbekannter Befehl …".
     * --ask/--serve '!ai' path untouched in behaviour; gateway core
       refactored into gateway_completion() (raises GatewayError with
       the German hint) + gateway_chat() wrapper (catches → plain
       answer), so '!entwurf' can react to gateway failures distinctly.
     * --check extended: prints imap host/user/drafts/password-set and
       honestly reports reachability + login outcome (problems → exit 1).
     * New env (all optional, defaults complete):
         IMAP_HOST=stalwart, IMAP_PORT=143, IMAP_MAIL_DOMAIN=opensme.local
         IMAP_USER=<MATRIX_USER>@<IMAP_MAIL_DOMAIN> (used as-is if it
           already contains '@')
         IMAP_PASSWORD (unset → falls back to MATRIX_PASSWORD, see
           below — that fallback is rejected by the live directory)
         IMAP_DRAFTS=Drafts (SOGo label: „Entwürfe")
         AI_BRIEF_LIMIT=8

2. docs/af-ai-T4-sogo.txt — this report (repo-root EXACT path; scope
   scripts/, docs/ respected; nothing written anywhere else).

LIMITATIONS / NOTES
-------------------
* No end-to-end room round-trip was replayed live: the running bot
  process still serves the pre-T1 script (restarting the deployed
  container is operator work). The dispatch addition is 3 lines in
  handle_event and uses the same send_text path that has served '!ai'
  in production; command semantics are fully covered by the harness.
* Drafts land in the BOT account's mailbox (testuser) — per design the
  user opens SOGo as that account to review & send. Per-recipient
  delegation (IMAP proxyauth into the requester's mailbox) is a
  possible v2 once app-password handling per user exists.
* '!brief' is deterministic (no LLM call) by design — works even with
  the gateway key unset; „key items" = newest senders/subjects.
* Host-side stalwart admin REST returned 401 (store-held password
  differs from deployed .env) — not needed for this task; noted so the
  app-password seeding step is done with the documented script, not
  the admin API.
