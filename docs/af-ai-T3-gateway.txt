DESIGN NOTES
  * Gateway-first, ollama-fallback: the LiteLLM gateway speaks the
    OpenAI-compatible /v1/chat/completions contract (Bearer
    LITELLM_MASTER_KEY, bare model names like glm-5.3-flash) and answers
    in <2 s, so openaiChat() uses stream:false and plain JSON parsing;
    ollamaChat() (stream:true NDJSON) stays untouched as the fallback
    when OPENAI_API_KEY is unset or the gateway call fails.
  * One dispatch point: only runAiHelper's default chat changed
    (ollamaChat → aiChat); routes, prompts and the {status, payload}
    contract are unchanged, and explicit input.chat injections still win.
  * Operator opt-in unchanged in spirit: both env unset → aiEnabled()
    false → 503 {enabled:false}; with only LITELLM_MASTER_KEY set the
    surface goes live via the gateway; OLLAMA_URL alone keeps the old
    local-model path.
  * LlmError shapes identical across both legs (same German user
    messages, technical detail on the error for server logs), so the
    routes' 502 mapping and the UI messaging need no branching.
  * The compose wiring maps LITELLM_MASTER_KEY → OPENAI_API_KEY without
    renaming anything inside the portal — swap OPENAI_BASE_URL to any
    OpenAI-compatible endpoint and the code follows.

KNOWN LIMITATIONS
  * No live LiteLLM reachable from this host — the gateway contract is
    pinned against fetch mocks (URL, Bearer header, body shape,
    choices[0].message.content parsing); first live deployment should
    smoke-test with LITELLM_MASTER_KEY set on portal-web.
  * openaiChat() reuses aiTimeoutMs() (default 120 s) for symmetry, even
    though the gateway is expected to answer in <2 s.
  * Fallback is single-shot: a failed gateway call is retried once via
    ollama, not in a loop; if both legs fail, the ollama error (the last
    attempt) surfaces.
